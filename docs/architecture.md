# Архитектура системы AquaControl

Документ описывает устройство прототипа: слои, потоки данных, ключевые решения и
границы, по которым «эмуляцию» можно заменить реальным железом.

## 1. Общая схема

```
┌───────────────────────────┐        MQTT         ┌───────────────────────────┐
│   Эмулятор Raspberry Pi   │  (telemetry/status/ │        Backend            │
│        (firmware/)        │   state/cmd/ack)    │        (backend/)         │
│                           │◄───────────────────►│                           │
│  ┌─────────────────────┐  │                     │  ┌─────────────────────┐  │
│  │  Физическая модель  │  │   ┌────────────┐    │  │   MQTT ingest       │  │
│  │  TankModel (step)   │  │   │  Mosquitto │    │  │  (paho, VERSION2)   │  │
│  └─────────┬───────────┘  │   │   broker   │    │  └──────────┬──────────┘  │
│            │              │   │ 1883/9001  │    │             │             │
│  ┌─────────▼───────────┐  │   └────────────┘    │  ┌──────────▼──────────┐  │
│  │ sensors / actuators │  │                     │  │ telemetry / alerts  │  │
│  └─────────────────────┘  │                     │  │ control / scheduler │  │
│      DeviceAgent          │                     │  └──────────┬──────────┘  │
└───────────────────────────┘                     │             │             │
                                                  │  ┌──────────▼──────────┐  │
      ┌──────────────────────┐   REST /  WS       │  │ SQLAlchemy / SQLite │  │
      │  Android (Compose)   │◄──────────────────►│  │ (телеметрия, пороги,│  │
      │  dashboard / charts  │   /ws/telemetry    │  │ алерты, расписания) │  │
      │  control / scenarios │                    │  └─────────────────────┘  │
      └──────────────────────┘                    │  push (console/FCM)       │
                                                  └───────────────────────────┘
```

Три процесса, связанные двумя контрактами:

- **MQTT-контракт** (`docs/mqtt-contract.md`) — между устройством и backend.
- **REST + WebSocket** — между backend и мобильным приложением.

Оба контракта независимы: устройство ничего не знает о приложении, приложение — о брокере.

## 2. Слои

### 2.1 Firmware — эмулятор устройства (`firmware/`)

| Модуль | Ответственность |
|--------|-----------------|
| `simulator/physics.py` | `TankModel` — истинное физическое состояние и его эволюция во времени (`step(dt)`). Связанная модель: нагреватель и свет греют воду, фильтр снижает TDS, испарение против автодолива (ATO) держит уровень. |
| `simulator/sensors.py` | `read_sensors(model)` — превращает истинное состояние в «показания датчиков» с гауссовым шумом и округлением. |
| `simulator/actuators.py` | `apply_command()` применяет команду к модели, `build_state()` формирует retained-состояние актуатора. |
| `agent.py` | `DeviceAgent` — MQTT-клиент: цикл публикации телеметрии, retained-состояний и статуса, подписка на `cmd/+`, отправка ack. |
| `config.py` | `DeviceConfig` — конфигурация из переменных окружения (`AQUA_*`). |

**Граница замены на реальное железо:** меняются только `sensors.py` (чтение GPIO/I²C
вместо модели) и `actuators.py` (переключение реле/ШИМ). `agent.py`, контракт MQTT и
весь backend остаются без изменений. Именно поэтому симулятор и «прошивка» живут в
одном пакете с единым интерфейсом.

**Fault injection.** `AQUA_FAULTS` включает неисправности (`heater_stuck_off`, `ato_off`,
`ph_drift`) — для демонстрации срабатывания алертов без ожидания естественного дрейфа.

### 2.2 Backend (`backend/app/`)

| Слой | Модули | Ответственность |
|------|--------|-----------------|
| Приём данных | `mqtt_client.py` | Подписка на топики устройства; хендлеры `_handle_telemetry/_status/_state`. Точка входа всей телеметрии. |
| Хранение | `db.py`, `models.py` | Движок SQLAlchemy, ORM-модели. SQLite по умолчанию, схема переносима на Postgres/TimescaleDB. |
| Доменные сервисы | `services/telemetry.py`, `alerts.py`, `control.py`, `scheduler.py`, `notifications.py` | Бизнес-логика: сохранение и агрегация телеметрии, оценка порогов и жизненный цикл алертов, публикация команд, планировщик автокормления/света, отправка push. |
| REST API | `api/*.py` | Роутеры FastAPI по ресурсам (devices, telemetry, control, thresholds, alerts, schedules, push). |
| Реальное время | `ws.py` | `WebSocketHub` — рассылка кадров telemetry/status/state/alert подключённым клиентам. |
| Конфигурация | `config.py` | `Settings` (pydantic-settings), префикс `AQUA_`. |
| Сборка | `main.py` | Создание приложения, CORS, lifespan (инициализация БД, старт MQTT и планировщика). |

### 2.3 Android (`android/app/`)

MVVM поверх Jetpack Compose:

- `data/` — DTO (`Models.kt`), Retrofit-интерфейс (`ApiService.kt`), клиент (`Network.kt`),
  WebSocket-поток (`TelemetrySocket.kt`), справочник метрик (`Metrics.kt`).
- `ui/AquariumViewModel.kt` — единый `UiState` (StateFlow), опрос REST + живой WebSocket с
  переподключением, все команды управления и CRUD расписаний/порогов.
- `ui/screens/` — четыре экрана: Dashboard, Charts, Control, Scenarios.
- `ui/components/` — переиспользуемые виджеты (в т.ч. `LineChart` на Canvas без сторонних библиотек).

## 3. Потоки данных

### 3.1 Телеметрия (устройство → приложение)

1. `DeviceAgent` каждые `telemetry_interval_s` вызывает `read_sensors(model)` и публикует
   JSON в `aquarium/{id}/telemetry` (QoS 0).
2. `mqtt_client._handle_telemetry` сохраняет каждую метрику отдельной строкой (`store_sample`)
   и вызывает `alerts.evaluate()`.
3. `evaluate()` сравнивает значения с активными порогами, открывает/закрывает алерты,
   при необходимости шлёт push (с дебаунсом).
4. Backend транслирует кадр в WebSocket-хаб; приложение получает его почти мгновенно.
5. Параллельно приложение периодически опрашивает `/telemetry/latest` и `/history` (графики).

### 3.2 Команда управления (приложение → устройство)

1. `POST /devices/{id}/control/{actuator}` → `control.send_command()` генерирует `cmd_id`
   и публикует в `aquarium/{id}/cmd/{actuator}` (QoS 1).
2. Агент применяет команду к `TankModel` под блокировкой, публикует новое retained-состояние
   в `state/{actuator}` и ack в `cmd/{actuator}/ack`.
3. `mqtt_client._handle_state` сохраняет состояние; хаб рассылает кадр `state` в приложение.

### 3.3 Автоматизация (планировщик)

`APScheduler` (`BackgroundScheduler`, `CronTrigger`) хранит задания, восстанавливаемые из БД
через `sync_all()` при каждом изменении расписаний. Задание кормления публикует команду
`feeder`; сценарий света — пару заданий on/off. ID заданий: `feed-*`, `light-on-*`, `light-off-*`.

## 4. Модель данных

- `Device` — устройство, `online`, `last_seen`.
- `Telemetry` — узкая схема: одна строка на `(device_id, ts, metric, value)` с составным индексом. Просто масштабируется и переносится на TimescaleDB.
- `ActuatorState` — составной PK `(device_id, actuator)`, состояние в JSON.
- `Threshold` — уникально по `(device, metric)`; `min/max/enabled`.
- `Alert` — флаг `active`, `severity`, `resolved_at`; отдельно метрические и «устройство offline».
- `FeedingSchedule`, `LightScenario` — правила автоматизации.
- `PushToken` — токены приложения для push.

## 5. Ключевые технические решения

- **Единый пакет «прошивки» для симулятора и реального железа** — переход на датчики не
  затрагивает контракт и backend.
- **Узкая схема телеметрии** (метрика-значение, а не колонка на параметр) — добавление метрики
  не требует миграции таблицы; естественно ложится на time-series СУБД.
- **Retained-сообщения + Last Will (LWT)** — новый подписчик сразу видит актуальное состояние
  и статус; внезапный обрыв устройства помечает его offline без опроса.
- **Разделение QoS**: телеметрия QoS 0 (поток, потеря отдельного отсчёта некритична),
  команды и состояния QoS 1 (доставка гарантирована).
- **Позднее связывание `db.SessionLocal`** (`from . import db; db.SessionLocal()`) —
  позволяет тестам подменять фабрику сессий на in-memory БД.
- **Абстракция push-провайдера** (`console`/`fcm`/`null`) — демо работает «из коробки»
  (лог в консоль), продакшн включается переменной окружения.
- **Дебаунс алертов** по `(device, metric)` — устойчивое нарушение порога не превращается
  в шквал уведомлений.
- **График на Canvas** в приложении — нет тяжёлых сторонних зависимостей, полный контроль над отрисовкой.

## 6. Безопасность и ограничения прототипа

- Брокер настроен на `allow_anonymous true` — **только для разработки**. Для продакшна нужны
  логин/пароль или TLS-сертификаты.
- API-ключ (`AQUA_API_KEY`) опционален и по умолчанию выключен; при установке защищает
  все пишущие/управляющие эндпоинты заголовком `X-API-Key`.
- `usesCleartextTraffic` в Android включён для обращения к локальному backend по HTTP —
  в продакшне заменяется на HTTPS.
- SQLite достаточен для прототипа; при росте нагрузки — переход на Postgres/TimescaleDB
  сменой `AQUA_DATABASE_URL`.

Подробности контракта обмена — в [`mqtt-contract.md`](mqtt-contract.md);
справочник REST — в [`api.md`](api.md).
